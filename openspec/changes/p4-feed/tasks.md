## 1. Build

- [x] 1.1 [tech-artist] The scheduler and loss machine (design 1, 2):
  - **What:** `FeedEvents` and `FeedLoss` ported in C# with `System.Random(seed)`, `IFeedSignals` with labelled stubs, and a headless schedule dump.
  - **Verify:** the "same seed, the same schedule" scenario over 15 000 fields against the legacy C#'s dump.

  **As built:**
  - *Where:* the engine-free core is `unity/Assets/_Project/Scripts/Feed/Core/` (asmdef `Fpv450.Feed.Core`, `noEngineReferences`, namespace `Fpv450.Feed`). `tools/feedcore` compiles those files for .NET. `tools/feedbench schedule --seed <n> [--fields <n>] [--current <0-1>] [--cut <field>[:abrupt]]` writes one row per field, and prints the summary, the digest and the stubbed signals to stderr. `tools/feedtests` runs `Tests/EditMode/Feed/` (asmdef `Fpv450.Feed.Tests`) outside Unity.
  - *The port:* `FeedEvents` and `FeedLoss` keep Godot's constants, draw order and structure. Each literal names its line in the verbatim copy. Godot 4.7.2's float `Mathf.Sin` and `Mathf.Pi` are `MathF.Sin` and `MathF.PI` (read off its GodotSharp).
  - *Unity's Mono:* it draws the same `System.Random` sequence. It evaluates float expressions in double precision, though, so the first port drifted a few ulps per field, and `N3Roll` accumulated the drift: the events matched, the bits did not. Every float operation is now cast to `float` (no-op on CoreCLR), and Unity matches bit for bit. New C# float math in the feed needs the same casts.
  - *The A/B:* the verbatim legacy files, compiled in a scratch project against Godot 4.7.2's own GodotSharp, dump the same rows. 12 runs of 15 000 fields: seeds 1–3, each timer-only at motor current 0 and 0.6, and with a faded and an abrupt cut at field 7500. Every diff is empty. The runs reach every state (Picture, PartialSnow, Blue, Snow, Black) and every tell (brightening, top tear, bottom tear, grain rise). EditMode pins ten of those digests (`FeedScheduleTests`). The Godot code gives 6.4–8.8 quality drops/min and 3.6–4.4 dropouts/min at seeds 1–3. Each drop's gap counts from its end, so the README's "about 10/min" reads high. The code stays unchanged.
  - *Signals:* `IFeedSignals` carries the K§11.8 list in its units (A, V, rad/s, dB, cd/m²…), with `SourceOf` per signal and `FeedSignalLog.Describe` for the log. Every signal on `StubFeedSignals` is a settable stub: a parked drone, no fiber (infinite margin and bend radius), a 6S pack at 25.2 V (Godot's), noon, no rain, a blank OSD. `FeedEvents.AdvanceTo` still takes Godot's 0–1 motor current. The amps-to-fraction scale and the dB-to-0–1 link margin are 1.2's.
- [x] 1.2 [tech-artist] The camera rig and the pass (design 1, 3):
  - **What:** the FPV camera at field resolution with extra FOV and the intrinsics, and `video_feed.gdshader` as the HLSL full-screen pass, stage by stage, constants literal.
  - **Verify:**
    - the still A/B scenario against the Godot original (design 2; stop and report if Godot is not installed)
    - the lens scenario

  **As built:**
  - *Where:* `Shaders/Feed.shader` (three blits: encode, field, output), `FeedFeature` on all three URP renderers (inert on any camera without a `FeedOutput`), `FpvCamera` (the rig), `FeedSettings` (`Settings/Feed/FeedSettings.asset`), `Core/FeedUniforms` (the per-field values; motor current over Godot's 68 A, link margin over 13 dB, assumed until 7d). `Scripts/Feed/Editor/`: `FeedSetup.Apply` re-derives the asset, the renderer features and `Scenes/FeedTest.unity`; `FeedCapture.Stills -feedField a-b[+cut|+hardcut][,...]` is the Unity side of Godot's `--video-field`, with `-feedInput` for the identical input frame; `FeedCapture.Lens` is the lens scenario.
  - *The port:* `fragment()` is ported line by line, each block naming its `gd:N` line. Godot ran it per screen pixel, but every term except the vignette and the border is constant along a field line, so the field pass runs once per line and column (1920 × 287, the odd field's half line included) and the output pass bob-deinterlaces it and draws the P8 border. Departures, none visible: the vignette is read at the line's centre (≤ 0.07 of a level); GLSL's `mod` and reversed-edge `smoothstep` are written out; gd:203 reads `tap[-1]` and `tap[17]` past its 17 taps, where both chroma windows weigh zero, so the port clamps the index. The scene is encoded to sRGB code values first, as Godot's 8-bit screen texture held them.
  - *The rig:* f = 1.005 half-widths at 0° uptilt, 16:9. With k1 = 0.33 (O1, on the scene read only) the render covers 1.434 half-widths: 77.52° vertical, the picture 105.8° across. URP has no per-camera render scale, so the FPV camera renders into its own target and a child output camera (culling nothing) draws the feed to the screen.
  - *The still A/B (FEED-00):* one identical input frame, the `sample_patch` frame Godot renders with the feed off, fed to both feeds: to Unity as `-feedInput`, to Godot as a full-screen canvas under its feed (a local scene in the scratch worktree, never committed), because mouse motion turned Godot's noclip camera during the first `+cut` captures. Seed 1, signals 1, 1, 0 on both, 1920 × 1080, six runs: `600-700`, `260-310`, `1360-1425`, `600-700+cut`, `603-640+cut` (staged), `603-612+hardcut` (bottom tear). The 367 per-field state lines are identical. Over 26 stages (baseline, N3, N4, both, the tell, the top and bottom tears, black, blue, recovery, a rising and a deep quality drop, the grain rise, every staged state) the worst per-channel mean difference is 0.038 % (limit 2 %), with the OSD masked (task 1.4). Per pixel, the mean absolute difference is ≤ 0.24 of a level in every field but 7 of the 23 snow fields: there the two shader compilers round the hash's multiply-adds differently for that field's `fw + 511`, so the snow is another draw with the same statistics (below 32 / white / above 224: 63.8 / 20.0 / 11.9 % against 63.9 / 20.0 / 11.9 %).
  - *The reduced render (D-017) failed the A/B, so the full-resolution read stays* (README fallback): the frame point-sampled to 1600, 1344, 1280 and 960 across keeps its means (≤ 0.02 %) but loses 19–54 % of its fine horizontal structure against Godot (the tree line 81–66 %, the grass 68–46 %), and a 960-column field pass loses 41–64 %. `sceneWidth` is 1920 samples across the picture's centre, so with the lens's coverage the render is 2754 × 1549 (2.06× a 1080p frame). Its cost is 1.8's to measure.
  - *The lens scenario:* a straight-line grid 10 m ahead through the rig and the feed, its bars traced and k1 fitted as K§11.4 measured it: k1 = 0.330 (four bars, 1840 points, 0.86 px residual), PASS against 0.33 ± 0.03; four vertical bars at ±30° and ±45° give f = 1.005 half-widths.

  **As built:**
  - *The player:* `NoclipFeed` hooks `SceneManager.sceneLoaded` and, when `TestRange` loads, goes on its main camera with an `FpvCamera` fed by `NoclipFeedSignals`, so neither `TestRange.unity` nor its builder changes. The settings asset moved to `Settings/Feed/Resources/` (same GUID) so a rig added at run time loads it in a player. A rig added from code begins at `Start`, once it has its settings and signals, and its clock runs on across off and on. **V** turns the feed off and on (GAL-02's key; off is the clean noclip view); **O** shows the review overlay: the feed's field, loss state and quality drop, and every K§11.8 signal's value in its unit beside its source, drawn by IMGUI over the picture, never through it. `-feed 0`, `-feedwidth <n>` and `-feedcost` are the team's options. `docs/test-range.md` lists all of them. Checked in the release player with injected keys (they need scan codes: the Input System reads physical keys): O drew the overlay, V logged `[Feed] off` and showed the clean view, V again restarted the rig at the field the clock had reached, Esc quit with 0.
  - *Signals (design 4):* the camera's angular rate is measured off its pose every frame in its own axes, from the rotation's vector part (the acos of the scalar part rounds a frame's turn at a few hundred fps to nothing), and labelled `noclip`, a third source beside `stub` and `physics` (the spec scenario names it). Every other signal stays its stub: no current and an intact link, so only the Godot timers' quality drops and recovering dropouts run, both seen in the player. The pass does not read the rate yet (C4, P5 come later). The OSD is blank until 1.4.
  - *A fix on the way:* the FPV camera's colour-only target made URP's render graph warn every frame in the player (33 195 lines, 8 MB, in one 100 s bench). The target now has a depth buffer, and `FeedFeature` imports a scene target with depth by its identifier with its colour's info, since a render graph import takes a colour or a depth format, never both.
  - *PLT-02's FPV row* (AC, Balanced plan, best performance mode, CPU 3.2 GHz, 1920 × 1080 full screen, vsync 0, D3D12, the test range's three legs, 30 s each after 2 s): at the full read (2754 × 1549) the yard averages 325 fps with a 1 % low of 203, the posadka at 2 m 332 and 198, the fields at 50 m 400 and 205. At 1600 (2295 × 1291): 341/136, 370/220, 415/160; at 1280 (1836 × 1033): 326/121, 347/160, 415/140. The feed off: 394/224, 416/216, 510/263. The frame is CPU-bound here, so the width barely moves it, and the 1 % lows wander by ±40 between runs (other agents shared the machine).
  - *The render size:* **the full read stays** (`sceneWidth` 1920): it holds the FPV row with a margin of 3.2× on the average and 3.3× on the 1 % low, so the pilot sees Godot's fine structure at G4.
  - *The cost (FEED-10):* `-feedcost` in the development player reads the GPU time of the "Feed" profiling sampler, which spans the three passes (encode, field, output), for 30 s at the start view after 2 s, same machine state as above. At the full read: mean 0.293 ms, 99th percentile 0.311, max 0.318, 3.0 passes a frame (within 1.0 ms, 71 % to spare; an earlier run gave 0.290). At 1600: 0.269 ms; at 1280: 0.258 ms: the encode pass scales with the render, the field and output passes do not. Unity's frame-timing GPU figure read 0.3 ms for the whole D3D12 frame, which cannot be, so it is not reported. The bigger render itself is the FPV camera's cost, in the frame rates above.
  - *Setup:* `ProjectSetup.Apply` calls `FeedSetup.ApplyFeature` (the settings asset and the feature on every renderer), not the whole `Apply`: rebuilding `FeedTest.unity` draws new file ids every run, which broke the setup's "a second run changes nothing" (seen on the first try: 6 878 changed scene lines; with `ApplyFeature` the tree stays clean). `Fpv450.Build.TestRange -developmentBuild` makes the development player the cost scenario needs, in `Builds/Windows-TestRange-Development/`: a release player records no GPU time for a profiling sampler.
  - *Later:* 1.7's AE/AWB adds a scene-luma read and its loop, so it re-measures the cost.
